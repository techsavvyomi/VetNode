1. Introduction

1.1 Project Overview

VetNode is an Internet of Things (IoT) based cattle health monitoring system designed to provide real-time, continuous surveillance of livestock vital signs. The system employs wearable sensor nodes attached to individual cattle to measure body temperature and heart rate, transmitting the collected data wirelessly to a centralized gateway unit using Long Range (LoRa) radio communication at 433 MHz.

The central gateway aggregates incoming telemetry, evaluates the readings against configurable health thresholds, and dispatches descriptive SMS alerts to the farmer's mobile phone via a GSM modem when anomalous conditions are detected. A built-in OLED dashboard provides on-site real-time visualization, while a menu-driven interface allows field configuration without requiring firmware re-flashing.

The project targets small to medium-scale dairy and cattle farms where veterinary resources are limited and early detection of health anomalies—such as fever, hypothermia, tachycardia, or bradycardia—can significantly reduce livestock mortality and improve farm productivity.

1.2 Problem Statement

Livestock health monitoring in rural and semi-urban farming operations remains predominantly manual, relying on periodic visual inspections and intermittent veterinary visits. This approach presents several critical limitations:

  • Delayed Detection: Symptoms of common bovine diseases such as mastitis, bovine respiratory disease (BRD), and tick-borne fever often manifest through subtle changes in body temperature and heart rate hours before visible clinical signs appear. Manual observation frequently misses these early indicators.
  • Scalability Constraints: As herd sizes grow, the labor and time required for individual animal assessment become unsustainable, leading to monitoring gaps and increased risk of undetected illness spreading within the herd.
  • Limited Connectivity: Rural farming areas often lack reliable internet infrastructure, rendering cloud-dependent IoT solutions impractical. A communication method that operates independently of Wi-Fi or cellular data networks is essential.
  • Cost Barriers: Commercial livestock monitoring systems are prohibitively expensive for smallholder farmers, creating an accessibility gap in precision livestock farming technologies.
  • Absence of Automated Alerting: Without continuous monitoring and automated notification mechanisms, abnormal health events during nighttime hours or when farm personnel are off-site go undetected until they escalate into emergencies.

1.3 Objectives

The primary objectives of the VetNode project are as follows:

  1. Design and implement a wearable, low-power sensor node capable of continuously measuring bovine body temperature and heart rate with clinically acceptable accuracy.
  2. Establish a reliable long-range wireless communication link between sensor nodes and a central gateway using LoRa modulation at 433 MHz, achieving effective coverage of 100–200 meters in typical farm environments.
  3. Develop a centralized gateway unit that aggregates multi-node telemetry, evaluates health thresholds, and dispatches descriptive SMS alerts via a GSM modem to the farmer's mobile phone.
  4. Implement a non-blocking, state-machine-driven firmware architecture that ensures responsive user interaction and uninterrupted data acquisition.
  5. Provide an on-device user interface with a real-time OLED dashboard and menu-driven configuration system, enabling threshold adjustment and system diagnostics without programming tools.
  6. Support multi-node operation with Time Division Multiple Access (TDMA) scheduling to prevent transmission collisions across simultaneously monitored cattle.
  7. Achieve a cost-effective, open-source solution accessible to smallholder farmers using commercially available, off-the-shelf components.

2. System Overview

2.1 High-Level Description of the Solution

The VetNode system follows a star-topology wireless sensor network architecture comprising two primary subsystems:

  1. Sensor Nodes (Wearable Units): Each node is an ESP32-based embedded device equipped with a MAX30102 pulse oximetry sensor for heart rate detection, a DS18B20 digital temperature sensor for body temperature measurement, and a DS3231 real-time clock for timestamping. The node continuously acquires sensor data and transmits structured telemetry packets via an SX1278 LoRa transceiver at 2-second intervals.
  2. Central Gateway (Base Station): The gateway is an ESP32-based receiver that monitors the LoRa channel for incoming node transmissions. It parses telemetry packets, updates per-node health records, evaluates readings against configurable thresholds, and triggers SMS alerts through a SIM800L GSM modem when anomalies are detected. A 128×64 SH1106 OLED display provides real-time dashboard visualization, and a two-button interface enables menu navigation and configuration.

The system operates entirely on the unlicensed 433 MHz ISM band for node-to-gateway communication and the 2G GSM network for alert delivery, making it independent of local internet infrastructure.

3. Architecture Design

3.1 System Architecture

The VetNode system adopts a two-tier, star-topology wireless sensor network architecture. At the edge layer, multiple wearable sensor nodes operate as independent data acquisition units, each responsible for a single animal. At the aggregation layer, a centralized gateway serves as the network coordinator, data processor, and communication bridge to the GSM cellular network.

Within each tier, the firmware follows a cooperative multitasking model built on non-blocking finite state machines. This architectural decision ensures that no single operation (sensor read, radio transmission, serial communication, or user interface update) monopolizes the processor, thereby maintaining system responsiveness and preventing watchdog timer resets.

The communication layer employs a unidirectional primary / bidirectional secondary pattern: nodes primarily transmit heartbeat and data packets to the gateway, while the gateway may optionally send command packets (LED control, pings) to specific nodes. This asymmetric design minimizes node power consumption while preserving remote diagnostic capabilities.

4.2 Component Descriptions and Roles

ESP32-WROOM-32 (Microcontroller)

The ESP32-WROOM-32 serves as the central processing unit for both the sensor node and gateway. Featuring a 32-bit Xtensa LX6 dual-core processor clocked at 240 MHz, 520 KB of SRAM, and 4 MB of flash memory, it provides ample computational resources for concurrent sensor management, radio communication, and user interface rendering. Its native support for SPI, I2C, and UART peripherals makes it an ideal platform for interfacing with the diverse set of sensors and communication modules required by this project.

SX1278 LoRa Transceiver (Communication)

The Semtech SX1278 is a sub-GHz LoRa spread-spectrum transceiver operating in the 433 MHz ISM band. It provides long-range wireless communication with high sensitivity (−148 dBm) and configurable link parameters. In this project, it is configured with a bandwidth of 125 kHz, spreading factor 7, coding rate 4/5, and transmit power of 10 dBm, achieving an effective range of 100–200 meters in line-of-sight farm conditions. The module interfaces with the ESP32 via the SPI bus using the RadioLib library.

MAX30102 Pulse Oximetry Sensor (Heart Rate)

The MAX30102 is an integrated pulse oximetry and heart rate sensor module with dual-wavelength (red and infrared) LEDs and a photodetector. In this application, the infrared channel is used for heart rate detection through photoplethysmography (PPG). The sensor is configured for a sample rate of 400 Hz with an 18-bit ADC resolution (411 μs pulse width), providing high-fidelity pulse waveform data. A custom beat detection algorithm processes the raw IR values to extract beats per minute (BPM) with a rolling 4-beat average.

DS18B20 Digital Temperature Sensor

The DS18B20 is a digital thermometer that communicates over a single-wire (OneWire) interface, providing temperature measurements with a factory-calibrated accuracy of ±0.5°C over the range of −10°C to +85°C. Its digital output eliminates the need for analog-to-digital conversion and associated calibration errors, making it well-suited for body temperature monitoring in the 37–42°C range relevant to bovine health.

DS3231 Real-Time Clock (Timekeeping)

The DS3231 is a high-precision I2C real-time clock with an integrated temperature-compensated crystal oscillator (TCXO), providing timekeeping accuracy of ±2 ppm (±1 minute per year). It serves as the timestamp source for sensor readings on the node side, enabling accurate temporal correlation of health data.

SIM800L GSM Module (Cellular Communication)

The SIM800L is a quad-band (850/900/1800/1900 MHz) GSM/GPRS module used exclusively on the gateway for dispatching SMS alerts. It interfaces with the ESP32 via UART (Serial2) at 9600 baud and is managed by a non-blocking state machine that handles AT command sequences for SMS transmission. The module requires a dedicated 5V power supply capable of delivering 2A peak current during radio bursts.

SH1106 128×64 OLED Display (User Interface)

The SH1106 OLED display provides a monochrome, high-contrast visual interface on the gateway. It renders the real-time dashboard showing cow identification, vital signs, LoRa signal quality, GSM status, and alert notifications. The display is driven via I2C using the Adafruit SH110X and GFX libraries, with support for automatic power-off after a configurable inactivity timeout.

5.2 Node Firmware Logic

The sensor node firmware (Node.ino, approximately 461 lines) implements a cooperative multitasking loop that manages sensor acquisition, LoRa transmission, command reception, and LED diagnostics. The key functional components are:

Sensor Initialization and Recovery

The attemptSensorInit() function initializes the MAX30102 pulse sensor with precisely tuned parameters: LED brightness of 0x1F, sample averaging of 4, dual-wavelength mode (Red + IR), sample rate of 400 Hz, and pulse width of 411 μs for 18-bit ADC resolution. If any I2C sensor (MAX30102 or DS3231) fails to initialize or becomes disconnected during operation, the system automatically retries initialization every 10 seconds while continuing to transmit available data with error flags.

Heart Rate Detection Algorithm

The processHeartRate() function implements a non-blocking, real-time beat detection algorithm:

  1. Finger Detection: The infrared (IR) reflectance value is compared against a threshold of 50,000 counts. Values below this threshold indicate no contact with the sensor surface.
  2. Beat Detection: A derivative-based peak detection identifies cardiac beats from the IR waveform.
  3. Interval Validation: Only beat intervals between 300 ms (200 BPM cap) and 2000 ms (30 BPM floor) are accepted.
  4. Warm-up Phase: The first 4 detected beats establish a baseline average before reporting.
  5. Outlier Rejection: Any beat interval deviating more than ±30% from the rolling average is discarded.
  6. Rolling Average: A 4-beat FIFO circular buffer computes a smoothed BPM value.
  7. Staleness Detection: If no beats are detected for 30 seconds, the heart rate reading is cleared to zero.

Temperature Acquisition

The readTemperature() function queries the DS18B20 sensor via the OneWire protocol, performing a single-point sampling. LED outputs are disabled during the read cycle to prevent electrical noise from affecting the measurement. A yield() call is inserted to prevent watchdog timer resets during the conversion delay.

Transmission Schedule

The node transmits two types of packets on a fixed schedule with TDMA offsets to prevent multi-node collisions:

  • Heartbeat (HB) Packets: Transmitted every 2000 ms, containing the full telemetry payload with error flags.
  • Data (DATA) Packets: Transmitted every 5000 ms after the warm-up period, containing validated sensor readings only.

Each node's transmission is offset by (COW_ID − 1) × 500 ms from the base interval, providing non-overlapping time slots for up to 4 nodes per cycle.

5.3 Gateway Firmware Logic

The gateway firmware (Gateway.ino, approximately 1410 lines) is a substantially more complex application managing radio reception, data processing, alert generation, GSM communication, OLED rendering, and user input. Its operation is governed by multiple cooperating state machines:

GSM State Machine

The handleGsmState() function implements a fully non-blocking state machine for SIM800L management:

Each state issues an AT command and transitions to a wait state that monitors the UART buffer for expected responses, with timeout handling for each step. This ensures that the gateway remains responsive during the 5–15 second SMS transmission process.

Alert Engine

The queueAlert() function serves as the centralized alert processor. When incoming telemetry values breach configured thresholds, it:

  1. Validates that the alert cooldown period (configurable, 1–60 minutes) has elapsed since the last alert for the same node.
  2. Constructs a descriptive SMS body including the cow ID, violation type, and current vital sign values (e.g., "ID:1 T_HI T:39.8 HR:75 (HB)").
  3. Activates the buzzer for three 100 ms beeps as an audible alert.
  4. Sets the gsmSmsPending flag, triggering the GSM state machine to initiate SMS delivery.

LoRa Auto-Recovery

The gateway continuously monitors the time since the last successfully received packet. If 30 seconds elapse without any reception, a "LORA LOST" warning is displayed on the dashboard. After 60 seconds of silence, the gateway automatically reinitializes the SX1278 module and rebroadcasts its sync word, attempting to restore the radio link without manual intervention.

Acknowledgment Node → Gateway ACK Response to PING

Packet Field Descriptions

  • seq: 16-bit unsigned sequence counter (0–65535), incremented per transmission, used for packet loss detection.
  • cowID: Integer identifier (1–9) assigned to each node, corresponding to the individual animal.
  • temp: Body temperature in degrees Celsius, floating-point with one decimal precision.
  • hr: Heart rate in beats per minute, integer value (0–255).
  • errFlag: Error status indicator — "0" for no error, "HR" for heart rate sensor error, "RTC" for clock error, "ALL" for multiple failures.

6. Implementation Details

6.1 Step-by-Step Working

The complete operational sequence of the VetNode system from power-on to alert delivery is described below:

Phase 1: Initialization (Power-On)

  1. Both the sensor node and gateway ESP32 boards power on and execute their respective setup() routines.
  2. The node initializes the I2C bus (GPIO 21/22), OneWire bus (GPIO 15), and SPI bus (GPIO 5/18/19/23).
  3. The MAX30102 sensor is configured with optimized parameters (LED brightness 0x1F, 400 Hz sample rate, 18-bit resolution).
  4. The DS3231 RTC is queried to verify I2C connectivity.
  5. The SX1278 LoRa module is initialized at 433 MHz with matched parameters on both node and gateway.
  6. The gateway initializes the SH1106 OLED, loads saved configuration from NVS, and boots the SIM800L GSM modem via the AT command handshake sequence.
  7. LED indicators on the node provide visual confirmation of successful initialization (green blink pattern).

Phase 2: Continuous Data Acquisition (Node)

  1. The main loop executes continuously, calling processHeartRate() on each iteration to sample the MAX30102 IR channel.
  2. When a cardiac beat is detected, the inter-beat interval is validated (300–2000 ms), checked against the rolling average (±30% tolerance), and added to the 4-beat circular buffer.
  3. Every 2000 ms (adjusted by TDMA offset), readTemperature() queries the DS18B20 and the node assembles a heartbeat packet.
  4. The assembled packet (HB,seq,cowID,temp,hr,errFlag) is transmitted via the SX1278 at 433 MHz.
  5. Between transmissions, the node monitors DIO0 for incoming command packets from the gateway.

Phase 3: Data Reception and Processing (Gateway)

  1. The gateway continuously monitors the DIO0 interrupt pin for incoming LoRa packets.
  2. Upon packet reception, the raw string is parsed to extract the packet type (HB or DATA) and individual fields.
  3. The extracted data is stored in the corresponding NodeData structure, indexed by cow ID, along with the RSSI value and reception timestamp.
  4. Sequence number tracking detects missing packets and updates the packet loss counter.

Phase 4: Threshold Evaluation and Alert Generation

  1. After updating the node data structure, the gateway compares the received temperature and heart rate values against the configured thresholds:
    • Temperature High: > 39.5°C (default)
    • Temperature Low: < 37.0°C (default)
    • Heart Rate High: > 90 BPM (default)
    • Heart Rate Low: < 50 BPM (default)
  2. If any threshold is breached and the cooldown period has elapsed, queueAlert() constructs a descriptive alert string.
  3. The buzzer emits three 100 ms beeps and the gsmSmsPending flag is set.

Phase 5: SMS Alert Delivery

  1. The non-blocking GSM state machine detects the pending SMS flag and initiates transmission.
  2. AT+CMGF=1 sets text mode, followed by AT+CMGS="<phone>" to address the recipient.
  3. The alert body (e.g., "ID:1 T_HI T:39.8 HR:75 (HB)") is sent, terminated by Ctrl+Z (ASCII 26).
  4. The state machine waits for the +CMGS: confirmation response from the GSM network.
  5. A "SMS SENT!" toast notification is displayed on the OLED for 3 seconds.

Phase 6: Dashboard Display and User Interaction

  1. The renderDashboard() function refreshes the OLED display every 3 seconds with the latest data.
  2. The display presents: firmware version header, GSM signal bars, cow ID, temperature, heart rate, LoRa RSSI bars, "Last Seen" elapsed time, and current alert status.
  3. Button presses are detected by scanButtons() with debouncing and routed to the appropriate UI state handler for menu navigation, configuration editing, or hardware testing.

6.2 Hardware–Software Integration

The integration of hardware and software in the VetNode system follows a layered abstraction approach:

  • Physical Layer: Electrical connections between the ESP32 and peripheral modules via standardized buses (SPI for LoRa, I2C for sensors and display, UART for GSM, OneWire for temperature, GPIO for LEDs and buttons).
  • Driver Layer: Third-party Arduino libraries (RadioLib, Adafruit GFX, DallasTemperature, MAX30105, RTClib) provide hardware abstraction, exposing high-level APIs for sensor reading, packet transmission, and display rendering.
  • Application Layer: Custom firmware logic implements the domain-specific behavior: beat detection algorithms, threshold evaluation, alert state management, TDMA scheduling, and the multi-screen user interface.

A critical integration consideration is the shared I2C bus on the node, where the MAX30102 (address 0x57) and DS3231 (address 0x68) coexist. The firmware ensures non-overlapping access through sequential polling in the main loop, avoiding bus contention. Similarly, LED outputs are disabled during DS18B20 temperature reads to prevent electrical noise interference.

7.3 Alert Threshold Behavior

The alert system was validated by simulating out-of-range conditions:

  • Temperature High Alert: When the DS18B20 sensor reported values exceeding 39.5°C, the gateway correctly identified the breach, activated the buzzer, displayed the alert on the OLED, and dispatched an SMS within 5–15 seconds.
  • Heart Rate Alerts: Simulated bradycardia (<50 BPM) and tachycardia (>90 BPM) conditions triggered appropriate alert responses with correct violation type identification in the SMS body.
  • Cooldown Mechanism: Repeated threshold breaches within the configured cooldown interval (default 5 minutes) were correctly suppressed, preventing SMS spam while maintaining the alert display on the dashboard.
  • Combined Alerts: Simultaneous temperature and heart rate violations generated a single combined SMS, reducing message overhead.
  • Graceful Degradation: When the MAX30102 sensor was physically disconnected, the node continued transmitting heartbeat packets with the "HR" error flag, and the gateway correctly displayed the degraded status without generating false health alerts.

8. Conclusion

8.1 Project Summary

The VetNode project successfully demonstrates a functional, cost-effective IoT-based cattle health monitoring system that addresses the critical gap in real-time livestock health surveillance for small to medium-scale farming operations. The system achieves its primary objectives of continuous vital sign monitoring, reliable long-range wireless data transmission, automated alert generation, and user-friendly field configuration.

The star-topology wireless sensor network, built on ESP32 microcontrollers with LoRa communication at 433 MHz, provides a robust and scalable platform for multi-animal monitoring without dependence on local internet infrastructure. The non-blocking firmware architecture, driven by cooperating finite state machines, ensures that sensor acquisition, radio communication, GSM alert delivery, and user interface rendering operate concurrently without mutual interference.

The integration of the MAX30102 pulse oximetry sensor with a custom beat detection algorithm (featuring 4-beat rolling averages, outlier rejection, and staleness detection) and the DS18B20 digital temperature sensor provides clinically relevant vital sign measurements with acceptable accuracy for early anomaly detection. The descriptive SMS alert system, delivered via the SIM800L GSM modem, provides farmers with actionable health information for immediate veterinary decision-making.

8.2 Key Learnings

  1. Non-Blocking Design is Essential: Blocking operations in embedded systems with concurrent I/O requirements lead to data loss, UI unresponsiveness, and watchdog timer resets. State-machine-driven architecture resolves these issues comprehensively.
  2. LoRa Parameter Synchronization: All LoRa parameters (frequency, bandwidth, spreading factor, coding rate, sync word) must be precisely matched between transmitter and receiver. Even minor mismatches result in complete communication failure.
  3. GSM Module Power Requirements: The SIM800L module requires significantly more current (2A peaks) than the ESP32's 3.3V regulator can supply. A dedicated 5V/2A power source is essential for reliable GSM operation.
  4. Sensor Noise Mitigation: Shared power rails and GPIO activity can introduce noise into sensitive analog measurements. Disabling LED outputs during sensor reads and implementing digital filtering significantly improve data quality.
  5. TDMA for Multi-Node Scalability: Simple time-slotted transmission scheduling effectively prevents packet collisions without the overhead of a full medium access control (MAC) protocol.
  6. Persistent Configuration Improves Usability: Storing user-configurable parameters in NVS eliminates the need for firmware re-flashing during field deployment, a critical usability improvement for non-technical users.
  7. Graceful Degradation over Hard Failure: Designing the system to continue operation with partial sensor failures (reporting error flags rather than halting) significantly improves field reliability.

9. Future Scope

The VetNode platform provides a solid foundation for several potential enhancements and extensions:

  1. Cloud Integration and Data Analytics: Integrating a Wi-Fi or GPRS uplink on the gateway to transmit telemetry data to a cloud platform (e.g., ThingSpeak, AWS IoT Core) would enable historical data storage, trend analysis, and predictive health modeling using machine learning algorithms.
  2. GPS-Based Animal Tracking: Adding a GPS module (e.g., NEO-6M) to each sensor node would enable geolocation tracking, providing insights into grazing patterns, movement anomalies, and geofencing alerts for escaped animals.
  3. SpO2 (Blood Oxygen) Monitoring: The MAX30102 sensor supports dual-wavelength (red + IR) pulse oximetry for blood oxygen saturation (SpO2) measurement. Implementing the SpO2 algorithm would add a clinically valuable vital sign without additional hardware.
  4. Solar-Powered Nodes: Integrating a small solar panel with a LiPo battery and charge controller would enable indefinite field deployment of sensor nodes without manual battery replacement.
  5. Mobile Application: Developing a companion mobile application (Android/iOS) with Bluetooth Low Energy (BLE) connectivity to the gateway would provide a richer user interface with graphical charts, historical data review, and remote configuration capabilities.
  6. Multi-Gateway Mesh Network: Extending the star topology to a mesh architecture with relay gateways would dramatically increase coverage area, enabling monitoring across large pastures and multiple farm zones.
  7. Accelerometer-Based Activity Monitoring: Adding an IMU (e.g., MPU6050) to sensor nodes would enable activity classification (standing, lying, walking, ruminating), providing additional behavioral health indicators.
  8. Machine Learning Anomaly Detection: Replacing fixed threshold alerts with a trained ML model that learns each animal's normal baseline patterns would reduce false positives and detect subtle health deviations earlier than static thresholds.
  9. Over-the-Air (OTA) Firmware Updates: Implementing ESP32 OTA update capability would allow remote firmware upgrades via Wi-Fi, eliminating the need for physical access to deployed nodes for software maintenance.
  10. Multi-Species Adaptation: The platform architecture is generalizable to other livestock species (goats, sheep, horses) with adjusted threshold ranges and additional species-specific sensors.
